# 第三章 建立 AI 开发工作流

AI Coding 的工作单位应该是一项可以检查的改变。一次要求完整实现所有系统，容易得到外观齐全、内部规则不一致的程序。把目标拆小，保留能够运行的版本，并在每次修改后验证，你才能持续知道项目处于什么状态。

## 先选择能够交付的路线

本案例使用 JavaScript 编写规则，HTML 和 CSS 实现界面，浏览器作为首发运行环境。这个选择适合小范围、以经营安排和信息反馈为主的游戏。若空间移动、精灵动画与镜头成为重要内容，可以评估 Phaser 等 2D 框架；它的官方定位是面向 Web 的 2D 游戏框架，支持 JavaScript 和 TypeScript。[官方说明](https://docs.phaser.io/phaser/getting-started/what-is-phaser)

不要同时学习多套引擎来完成同一版案例。选型表只比较当前需求：能否表达玩法、素材如何导入、能否导出目标平台、出错时如何检查。记录所选版本和原因，再通过一个最小页面验证环境。

基础环境需要编辑器、受支持的 Node.js、浏览器和 Git。安装后检查版本命令，运行一个页面，再让它显示一条状态。环境问题与游戏逻辑问题分开处理；空白页先看控制台和网络请求，而不是让 AI 重写玩法。

## 给 AI 一个可靠的项目上下文

项目根目录放一份简短的协作说明，包含目标、技术栈、目录职责、运行方式、规则来源与禁止随意改变的约定。它帮助 AI 在新会话里找到依据，也帮助你检查自己是否改变了方向。

```text
项目：街角餐厅，浏览器单人经营游戏。
规则来源：docs/design.md；数值来源：src/config.js。
core/ 只处理状态与规则，不访问 DOM 或浏览器存储。
ui/ 展示状态并发出命令，不重复计算营业结果。
改动前说明涉及文件；保持每个任务能独立运行与验收。
不得把密钥写入前端；未经说明不得删除存档迁移逻辑。
```

上下文应少而准确。十份互相矛盾的旧设计，比一份简短现行规则更危险。保留修改历史，但明确哪个版本生效。每轮任务提供相关文件和必要日志，不把全部仓库复制成一段难以判断的提示。

## 把需求拆成纵向的小步骤

“实现订单系统”仍然太大。可以拆成生成一个订单、检查库存、开始制作、完成收款、取消订单和显示失败原因。每步都打通规则到界面的最小链路，使你能够观察到实际变化。

任务卡写五项：背景、目标、边界、验收、验证方式。例如：

```text
背景：已有现金和简餐库存，界面可以显示状态。
目标：增加“采购 5 份简餐食材”命令，总价 40。
边界：只允许营业前采购，不能透支；本任务不加入折扣与赊账。
验收：现金 100 时变为 60，库存增加 5；现金 39 时状态不变并提示。
验证：运行相关规则检查，再用界面分别尝试成功与失败情境。
先检查现有状态结构，再实现，最后说明修改文件与验证结果。
```

数字使验收具体，边界防止顺手扩展。对“状态不变”也要检查：失败时不能先扣钱再退钱，导致日志、成就或其他监听器误触发。

## 用版本管理降低修改成本

建立第一个能运行的版本后提交到 Git。每次完成一个独立任务，检查差异、执行验证再提交。提交说明描述行为，例如“禁止营业中采购并显示原因”，方便日后定位。

```bash
git status
git diff
git add src/core/purchase.js src/ui/shop.js
git commit -m "限制采购阶段并增加失败提示"
```

添加文件时注意不要提交密钥、本机缓存或临时日志。公开仓库中的秘密不能靠删掉最新文件解决，因为旧提交可能仍然保留。开发过程中尽量不引入需要密钥的在线服务；若确实需要，应把密钥保存在服务端。

合并新工作前，知道当前基线可以做什么。出问题时先保存未提交改动，再比较版本。不要因为 AI 建议执行清理命令，就丢弃自己尚未记录的工作。

## 调试时提供证据

好的错误报告包含预期、实际、复现步骤、输入状态、错误日志和版本。比如“采购两次后库存变负”比“采购坏了”更容易定位。先找最短路径，减少不相关操作。

可以让 AI 按下面的顺序处理：列出可能原因，说明需要观察的证据，添加最少日志，定位后修改，并验证原来失败的路径。避免每次失败就整体替换模块，因为大改动会同时引入更多未知。

假设 AI 把采购成本扣了两次。你应要求它追踪谁拥有扣款职责：按钮处理函数扣了一次，核心命令又扣一次。修复应保留单一入口，再检查其他命令是否也有重复计算。这个示例是诊断方法，不是某次实际运行记录。

## 控制工具调用成本与权限

复杂任务先让 AI 读相关文件并给出短计划，简单任务直接实现。每完成一个阶段，记录有效结论，后续引用它们，减少重复研究和上下文堆积。不要为了少一次调用，把所有功能塞进一个无法验收的任务。

文件编辑、依赖安装、账号连接和公开发布具有不同影响。明确当前任务授权范围，公开前检查输出目录和提交内容。AI 的工作记录可以帮助审查，但真正交付的是经过验证的文件与版本。

工具名称会变，任务卡与验收方式可以保持。选择你能访问的编程助手即可，不需要在书中绑定某个模型型号。涉及具体命令时，以实际安装版本的官方文档为准。

## 零基础先认识四种东西

项目是一个文件夹，源码是里面可以编辑的文本，程序运行时读取这些文本，构建则把它们整理成可发布文件。终端是输入命令的窗口，不需要把它理解成另一种编程语言。先分清“我在编辑哪个文件”和“我在运行哪个目录”，能减少很多初学者错误。

HTML 负责页面结构，CSS 负责颜色与布局，JavaScript 负责行为。案例里，`index.html` 放按钮和容器，`style.css` 定义视觉，`core.mjs` 处理经营规则，`ui.mjs` 连接按钮、画面与声音。`.mjs` 表示 JavaScript 模块，可以通过导入共享规则。

不必先完整学习四类文件。先打开案例，找到采购按钮；再让 AI 从点击追踪到 `purchase` 函数；最后找到现金改变的位置。这个小过程让“界面”和“逻辑”的区别具体起来。

## 第一次在本机运行

从阅读站点下载[餐厅案例 ZIP](https://linghugoogle.github.io/ai-coding-simulation-games/downloads/restaurant.zip)，解压到一个容易找到的位置，例如桌面上的 `restaurant`。不要直接在压缩包里编辑。确认文件夹内有 `index.html`、`core.mjs`、`ui.mjs`、`style.css`、`assets.svg` 和 `serve.mjs`。

安装一个代码编辑器和受支持的 Node.js，重新打开终端后输入 `node --version`。看到版本号后继续；如果提示找不到命令，先检查安装与终端重启。安装来源使用官方渠道，不要把未经核实的安装脚本整段粘进终端。

在编辑器中打开整个 `restaurant` 文件夹，再打开集成终端。终端当前目录应是这个文件夹，输入：

```bash
node serve.mjs
```

程序会打印本机地址。将它复制到浏览器，看到“街角餐厅”即成功。终端要保持打开；停止时在该终端按 Ctrl+C。如果端口被占用，先关闭自己之前启动的服务，或按报错给出的方式换端口。

不要双击 `core.mjs`，也不要把 Node 命令输入浏览器地址栏。浏览器请求本地服务中的文件，Node 负责提供这些文件。把这一步做通之后，后续修改才有稳定的查看入口。

如果从整本书仓库开始，在根目录执行 `npm ci`、`npm run dev`，再打开终端输出地址。案例可从首页入口进入。`npm ci` 按锁文件安装依赖，`npm run dev` 执行项目预先定义的开发命令；命令失败时先读第一条错误。

## 第一次修改不需要设计能力

在 `core.mjs` 找到 `DISHES` 对应的菜品配置。找到简餐的 `price:20`，只把二十改成二十二，保存并刷新。营业前界面中的简餐原价应变为二十二。不要同时改成本与时间。

然后采购五份并开始营业，观察收款是否按新价格发生。完成后把价格恢复到二十。这个练习让你体验查找、修改、保存、刷新和验证，暂时不涉及复杂系统。

如果页面变空白，检查逗号、引号和括号是否被删掉，打开浏览器开发者工具的 Console 查看错误。把第一条错误及相邻代码交给 AI，要求最小修复，不要重建整个游戏。

## 不会描述需求时用这个句式

“在什么情境下，我做了什么，希望看到什么，现在看到什么。”例如：“在营业前，点击简餐采购按钮，现金应该减少四十、库存增加五；现在现金减少八十。请先追踪按钮与 `purchase`，只修重复扣款。”这就是一张有效的任务卡。

请求界面修改时，补上位置与优先级：“我希望日报先显示利润，再显示流失原因，手机上不要左右拖动。”请求视觉修改时，提供参考与限制：“沿用当前奶油底色和深绿按钮，只调整菜单区域，保留文字可读性。”不需要先懂专业术语。

可以让 AI 在实现前把需求复述成三条验收条件。你确认它理解了之后再执行。若条件仍然模糊，先补例子。一次增加一句明确限制，通常比一大段“更专业、更高级”有效。

## 学会看一次修改差异

让 AI 列出修改文件、每个文件的目的和验证结果。打开编辑器的差异视图，红色一般表示删除，绿色一般表示新增。你不必理解每行代码，但能检查是否出现任务之外的大量文件改动。

一个按钮文案任务如果同时更改存档和订单计时，应暂停并要求解释。依赖升级、目录迁移和资源替换都有自己的风险，最好独立进行。任务越小，你越容易判断正确与否。

没有使用 Git 前，可先复制一份干净案例作为练习备份；熟悉运行后再按前文建立提交。不要长期靠“最终版二”“最终版真的最终”管理。Git 的作用是记录可以比较和回到的状态。

## 给初学者的协作底线

不把看不懂的系统清理命令直接执行；不把私人文件、账号密钥和完整电脑日志发送到无关服务；不让 AI 为了修页面而删除原有存档。遇到账号、付费和公开发布时，自己确认目标与内容。

这不会阻止你使用 AI，反而让它的帮助可持续。你负责目标、输入与验收，AI 负责在清楚边界中实现和解释。逐步理解，是整个协作流程的一部分。

## 常见报错如何处理

| 看到什么 | 先检查什么 | 给 AI 的信息 |
| --- | --- | --- |
| 找不到 node 命令 | 安装与终端是否重新打开 | 系统类型、版本检查结果 |
| 找不到 serve.mjs | 当前目录与解压位置 | 文件列表、执行命令 |
| 端口被占用 | 是否已有自己启动的服务 | 完整端口错误，不附账号密钥 |
| 页面空白 | 控制台第一条错误与网络请求 | 复现步骤、相关代码与日志 |
| 修改没变化 | 是否保存、页面是否刷新 | 修改文件路径与预期位置 |
| 数值异常 | 是否重复调用或错误类型 | 修改前后输入与状态 |

先解决第一条明确错误，再看后续错误是否消失。不要把整个电脑环境重装作为默认修复。项目能运行时保存基线，失败时优先退回最近一次小改动。

初学者可以直接要求：“我不知道这条错误是什么意思，请用当前文件解释，给最短检查步骤，每次只让我执行一项。”有效协作并不要求你先知道答案，但要求证据清楚。

## 最后动手验证

建立项目骨架和协作说明，让页面显示起始现金。用 AI 完成一个采购任务，检查成功和失败两个路径，再保存一个提交。关闭页面后重新启动，确认运行过程可以复现。

你需要能说清楚规则写在哪里、界面在哪里、如何运行、如何验证和如何回到上一版。能够回答这些问题，才算建立了可以持续开发的工作流。
