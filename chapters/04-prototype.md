# 第四章 实现可玩原型

原型要回答一个高风险问题：玩家是否能从经营结果中发现原因，并愿意改变下一天的安排？如果它只展示数字上涨，却没有形成调整动机，继续增加内容很难解决问题。

## 先做纸面与表格实验

用第二章的三道菜和固定费用，比较几种菜单与产能配置。配套 `examples/economy.mjs` 计算给定销量下的收入、成本、现金和库存。它可以帮助验证账目，但不模拟顾客到店、排队和满意度，不能从它的结果直接推出完整游戏好玩。

改变一个参数，写下预期，再计算结果。例如增加采购但保持销量，利润不因未售库存直接下降，现金却会减少；如果加入报废，利润也会受到影响。每次扩展模型都同时更新定义与测试。

表格解决确定性关系，可玩原型解决时间、信息与体验。两者相互补充。不要试图用一个静态表格证明实时排队体验，也不要让华丽动画掩盖错误账目。

## 选一个最小闭环

首个原型只有一间房、一道菜、一个工位。玩家在营业前输入采购量，开始后顾客依次到来，订单进入制作，完成后收款，最后扣固定费用并显示日报。没有足够库存的订单失败，并给出原因。

先规定时间：营业接单窗口持续 180 个模拟秒，关闭后不再生成顾客，已开始的工作按设计完成或取消。本案例建议允许已接订单继续处理，并把加班规则暂时简化为无额外费用；这个选择必须在后续平衡时重新评估。

闭环完成后，加入第二种菜和第二个可选升级。这时菜单与瓶颈才有机会形成选择。装饰、随机事件与顾客性格等待核心假设获得初步支持。

## 建立可检查的状态

状态是程序对当前局面的完整描述。下面是教学结构：

```js
const state = {
  version: 1,
  phase: 'planning',
  day: 1,
  cash: 1000,
  inventory: { simple: 0 },
  orders: [],
  kitchen: { currentOrderId: null, remaining: 0 },
  report: { revenue: 0, served: 0, lost: {} }
};
```

状态不要包含按钮节点、动画对象或打开的音频。这样才能容易序列化、保存和重放。菜品参数放配置，订单记录菜品标识和当前状态。若需要支持营业中改价，订单应保留接单时价格，避免交付时价格被新设置改变。

核心命令接收状态和参数，返回新状态或明确结果；界面调用命令并重新渲染。先不追求复杂设计模式，重点是同一笔资源变化只有一个负责位置。

## 让模拟时间与画面帧分开

浏览器画面更新频率会变化。若每帧固定增加收入或等待时间，高刷新率设备会改变规则。把经过时间换算成模拟步长，按固定规则推进。

```js
let accumulator = 0;
const step = 0.1;
function update(realDeltaSeconds) {
  accumulator += Math.min(realDeltaSeconds, 0.25);
  while (accumulator >= step) {
    simulate(step);
    accumulator -= step;
  }
  render();
}
```

这段示意选择在短时卡顿后限制追赶量，超出的现实时间不会全部补算。隐藏标签页时直接暂停，返回时提示玩家继续。若游戏要支持离线收益，需要另行定义，不能把浏览器挂起当作可靠模拟。

暂停时不调用规则推进；加速改变模拟推进速度，不改变订单耐心的单位。先保证一倍速正确，再加入加速。所有计时都统一使用模拟秒。

## 用队列解释生产

订单先进入等待队列，工位空闲时取出一单，检查并预留库存，开始制作。完成时触发一次交付。最好用明确状态，例如等待、制作、已完成、已取消。每种状态允许哪些转移写成表。

连续点击开始按钮不能生成两个营业循环；重复收到完成事件不能重复收款；取消订单不能留下永久占用工位。把这些情境当作原型阶段的基本验证，而不是到上线前再补。

若顾客耐心会耗尽，先区分等座与等餐。它们对应不同瓶颈。原型可以只做等餐，再在完整开发阶段加入座位，但报告名称要准确，不能把所有流失写成“服务不好”。

## 画面先服务诊断

用矩形代表厨房和桌子，用文字列出队列。显示现金、库存、当前订单、剩余时间和最近事件。这个版本看起来简陋，却应能解释每一次结果。

给测试者三个动作：采购、开始营业、查看日报。观察他能否不依靠作者说明完成一轮。若他不知道该点哪里，先修布局与标签；若他知道操作却没有想调整的事情，再回到规则。

## 将 AI 任务写成实验

```text
目标是假设验证：菜单选择能否改变厨房排队。
现有一工位、一菜品的原型已运行。
请加入第二种菜，读取统一配置，保留接单时价格。
先不要加装饰、剧情与音效。
增加可固定输入订单序列的调试入口，方便比较同一组订单。
验收：切换菜单后处理时长改变；库存只扣一次；结果可复现。
```

让 AI 提供手动验证步骤，并实际执行。固定输入用于比较方案；正常游玩仍可使用随机到店。把种子或订单列表保留下来，后续发生问题时更容易复现。

## 本章实践与验收

记录两次使用相同订单输入、不同菜单安排的营业结果。写下改变、预期、结果和解释。请一位未参与开发的人尝试，并记录他在何处停下、误解什么、是否主动开始下一天。

若没有形成下一轮调整，优先检查信息是否清楚、行动是否有效、反馈是否及时。达到“能玩、能解释、能比较”后，再投入成套素材和更完整功能。
